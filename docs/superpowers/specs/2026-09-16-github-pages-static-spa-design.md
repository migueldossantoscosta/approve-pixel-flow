# Design: Convert ProofSync to a static SPA deployable on GitHub Pages

## Context

ProofSync is currently built with TanStack Start (SSR + Nitro server, Cloudflare
target) and relies on three server functions (`getReviewByToken`,
`addPinByToken`, `approveVersionByToken` in `src/lib/review.functions.ts`) that
run on a server and use a Supabase **service-role** key to sign private storage
URLs for the public review page.

GitHub Pages only serves static files — it cannot run a Node/Nitro server or
any server function. To deploy on GitHub Pages, the app must become a pure
client-side SPA with no server-side code path.

Target repo: `https://github.com/migueldossantoscosta/approve-pixel-flow`
(not a `<user>.github.io` root repo), so the published site will live at
`https://migueldossantoscosta.github.io/approve-pixel-flow/` and the app must
be built with `base: '/approve-pixel-flow/'`.

## Goals

- The app builds to a static `dist/` folder with no server runtime dependency.
- All data operations (including the three public review operations) run
  entirely from the browser using the Supabase publishable key.
- Client-side routes (`/review/$shareToken`, `/dashboard`, etc.) work on
  GitHub Pages, including hard refreshes and direct links.
- A real landing page replaces the Lovable placeholder at `/`.
- GitHub Actions builds and deploys the site to GitHub Pages automatically on
  push to `main`.

## Non-goals

- No change to the Supabase data model, RLS policies, or RPC function logic
  (`get_review`, `add_pin_by_token`, `approve_version_by_token` stay as-is).
- No new product features (email notifications, PDF export, etc. — deferred).
- No attempt to keep SSR or any server function alive elsewhere; this is a
  one-way move to a static SPA for this deployment target.

## Architecture changes

### 1. Drop TanStack Start / SSR, switch to plain TanStack Router SPA

- Remove `src/server.ts`, `src/start.ts` (Nitro server entry + Start
  middleware — no longer meaningful without a server).
- Add `src/main.tsx`: standard Vite SPA entry — `ReactDOM.createRoot` +
  `RouterProvider` using the router from `src/router.tsx`.
- Add a plain `index.html` at the project root (Vite convention) with the
  `<head>` meta tags currently generated by `__root.tsx`'s `head()` /
  `shellComponent` (title, description, og/twitter tags, favicon,
  viewport/charset).
- Simplify `src/routes/__root.tsx`: drop `shellComponent`, `HeadContent`,
  `Scripts` (Start-only), keep `component`/`notFoundComponent`/
  `errorComponent` and the `QueryClientProvider` wrapper.
- Replace `vite.config.ts`'s `@lovable.dev/vite-tanstack-config` wrapper
  (which bakes in the Nitro/Cloudflare server target) with a plain Vite
  config: `@vitejs/plugin-react`, `@tanstack/router-plugin`'s Vite plugin
  (router-only, no Start plugin), `@tailwindcss/vite`, `vite-tsconfig-paths`,
  and `base: '/approve-pixel-flow/'`.
- Remove the `nitro` devDependency; it's unused once Start is gone.
- Drop `ssr: false` from `src/routes/_authenticated/route.tsx` (meaningless
  once there's no SSR at all — plain client-side `beforeLoad` still works the
  same way).

### 2. Replace server functions with direct client-side Supabase calls

`src/lib/review.functions.ts` currently wraps three Supabase RPC calls in
`createServerFn`. Since these RPCs are already `SECURITY DEFINER` and granted
to `anon` (they validate the share token inside Postgres), they can be called
directly from the browser using the existing publishable-key client
(`@/integrations/supabase/client`) — the same pattern the dashboard routes
already use for creator-side CRUD.

Rewrite the file to export plain async functions (no `createServerFn`, no
`inputValidator`) that:
- keep the same UUID/coordinate/length validation currently done in
  `inputValidator` (moved into plain JS guards),
- call `supabase.rpc('get_review' | 'add_pin_by_token' | 'approve_version_by_token', ...)`
  directly,
- for `getReviewByToken`, replace `signImages()` (which needed the
  service-role key) with `supabase.storage.from('deliverables').getPublicUrl(path)`
  for each version's image — no signing, no expiry, no admin client.

Update `src/routes/review.$shareToken.tsx` to call these functions directly
instead of via `useServerFn(...)`.

Delete `src/integrations/supabase/client.server.ts` (service-role admin
client) and the unused `src/integrations/supabase/auth-middleware.ts`
(`requireSupabaseAuth`) — both become dead code once there is no server to
run them on.

### 3. Storage bucket becomes public-read

Add a new Supabase migration:

```sql
update storage.buckets set public = true where id = 'deliverables';
```

Public buckets serve objects directly via `/storage/v1/object/public/...`
without going through RLS for reads, so no new SELECT policy is needed. The
existing owner-scoped INSERT/UPDATE/DELETE policies (migration
`...cfca78f6...sql`) still protect writes — only authenticated creators can
upload/modify their own files, exactly as today.

**Trade-off (already agreed):** deliverable images lose the 4-hour signed-URL
expiry and become permanently fetchable by anyone who has the exact storage
path (a random UUID-based path — not discoverable without the share link).
This matches approach "A" already approved.

**This migration must be run manually against the live Supabase project**
(via the Supabase SQL editor or CLI) — I have no direct database credentials
or Supabase CLI session from this environment to apply it myself.

### 4. Real landing page at `/`

Replace the Lovable placeholder in `src/routes/index.tsx` with a minimal
landing page: product name/one-liner (from the README's product overview),
a "Dashboard" call-to-action linking to `/auth` (which itself redirects to
`/dashboard` if already signed in). No new design system — reuse existing
Tailwind utility classes / shadcn `Button` component already in the project.

### 5. GitHub Pages SPA routing fix

GitHub Pages has no server-side rewrite rules, so a hard refresh or direct
link to e.g. `/review/abc-123` would 404. Use the standard
rafgraph/spa-github-pages redirect trick:
- `public/404.html`: a small script that redirects to `/` while encoding the
  original path/query into the URL as a query string.
- A matching small script added to `index.html` that decodes that query
  string back into the real path via `history.replaceState` before the
  router mounts.

### 6. GitHub Actions deployment

Add `.github/workflows/deploy.yml`:
- Trigger on push to `main` (and manual `workflow_dispatch`).
- Use `oven-sh/setup-bun` (project uses Bun — `bun.lock`/`bunfig.toml`).
- `bun install`, then `bun run build`, injecting the six `VITE_*`/`SUPABASE_*`
  build-time env vars from GitHub Actions **repository variables/secrets**
  (values copied from the local `.env` — publishable/anon-safe values, but
  kept out of the repo itself, consistent with the `.env`/`.env.example`
  split already done).
- Upload `dist/` via `actions/upload-pages-artifact` and deploy via
  `actions/deploy-pages`.
- Repo settings: Pages source must be set to "GitHub Actions" (a one-time
  manual step in the repo's Settings → Pages — I'll flag this at deploy time
  since I can't change repo settings without pushing/being granted access
  first).

## Risks / open items

- **Public bucket is a real, if narrow, security trade-off** — already
  discussed and accepted (approach A) in favor of avoiding extra
  infrastructure (Supabase Edge Functions).
- **The storage-bucket migration must be applied manually** by the user
  against their live Supabase project; I cannot run it from here.
- **Pushing to GitHub and enabling Pages** requires explicit user
  confirmation at that step (publishing to a shared/public system).
- Google OAuth (`@lovable.dev/cloud-auth-js`) is called from the browser
  already and should keep working unchanged in a pure SPA, but this hasn't
  been tested end-to-end in this environment (no Supabase/GitHub credentials
  available here) — worth a manual smoke test after deploy.

## Testing plan

- `bun run build` locally succeeds and `bun run preview` (or `vite preview`)
  serves a working SPA at `/approve-pixel-flow/` locally.
- Manually exercise: sign in, create project/deliverable, upload a version,
  open the public `/review/$shareToken` link in an incognito-equivalent
  session, place a pin, approve a version — confirms the RPC-direct calls and
  public image URLs work without any server function.
- Confirm a hard refresh on `/review/$shareToken` (simulated via the built
  `dist` served locally, or after real deploy) doesn't 404.
